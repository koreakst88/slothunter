# US Visa Slot Bot
## Roadmap & Техническое задание
**Версия 1.0 | Май 2026**

---

## 0. Обзор проекта

Бот автоматически мониторит доступные слоты для записи на визовое собеседование в Посольстве США (Астана, Казахстан) и переносит существующие брони клиентов с дальних дат на более ближние. Целевая аудитория — граждане РФ у которых текущие даты записи стоят на 2027-2028 год.

### Ключевые параметры

| Параметр | Значение |
|---|---|
| Целевая аудитория | Граждане РФ с записью на визу США |
| Консульство | Астана, Казахстан (facility_id = 134) |
| Сайт | ais.usvisa-info.com/ru-kz/niv |
| Минимальный порог переноса | Дата > сегодня + 2 месяца |
| Лимит переносов на аккаунт | 3 попытки (системное ограничение сайта) |
| Стек | Node.js + TypeScript, Telegraf, Supabase, Railway |
| Интерфейс агента | Telegram бот |

### 1.2 База данных Supabase

**Таблица: clients**

| Поле | Тип | Описание |
|---|---|---|
| id | uuid | Первичный ключ |
| name | text | Имя клиента (для отображения агенту) |
| email | text | Email для логина на сайте |
| password_encrypted | text | Зашифрованный пароль |
| schedule_id | text | ID расписания из URL сайта |
| applicant_ids | text[] | Массив ID заявителей в аккаунте |
| current_date | date | Текущая дата брони |
| status | text | active / paused / done / blocked |
| attempts_left | int | Осталось попыток переноса (макс 3) |
| created_at | timestamp | Дата добавления клиента |

**Таблица: logs**

| Поле | Тип | Описание |
|---|---|---|
| id | uuid | Первичный ключ |
| client_id | uuid | Ссылка на клиента |
| action | text | check / reschedule / error / notify |
| result | text | Результат действия |
| date_found | date | Найденная дата |
| date_booked | date | Забронированная дата (если перенос) |
| created_at | timestamp | Время события |

### 1.3 Эндпоинты сайта

| Действие | Метод | URL |
|---|---|---|
| Логин | POST | `/ru-kz/niv/users/sign_in` |
| Адрес консульства | GET | `/ru-kz/niv/schedule/{schedule_id}/appointment/address/134` |
| Доступные даты | GET | `/ru-kz/niv/schedule/{schedule_id}/appointment/days/134.json?appointments[expedite]=false` |
| Доступное время | GET | `/ru-kz/niv/schedule/{schedule_id}/appointment/times/134.json?date={date}&appointments[expedite]=false` |
| Перенести запись | POST | `/ru-kz/niv/schedule/{schedule_id}/appointment` |

### 1.4 Логика мониторинга (главный цикл)

1. Cron запускается каждые 5-8 минут (рандомный интервал)
2. Из Supabase берём всех клиентов со статусом `active`
3. Для каждого клиента по очереди:
   - Логин → получить CSRF токен и сессионные куки
   - GET `days/134.json` с applicant_ids клиента
   - Если дат нет — пропустить, логировать, перейти к следующему
   - Если есть дата: проверить что она > сегодня + 2 месяца
   - Если дата подходит: GET `times/134.json` для этой даты
   - Если `available_times` не пустой: переходим к переносу
   - Если `attempts_left == 1`: НЕ переносить, уведомить агента, ждать подтверждения
   - Если `attempts_left >= 2`: выполнить POST перенос автоматически
   - После переноса: обновить `current_date`, `attempts_left--`, `status = done`, уведомить агента
4. Задержка 10-15 секунд между клиентами
5. После полного круга — ждать следующего cron тика

## 2. Фаза 1 — Мок-сервер

Мок-сервер полностью имитирует `ais.usvisa-info.com`. Весь код бота пишется и тестируется против мока. Реальный сайт не затрагивается на этом этапе.

### 2.1 Эндпоинты мок-сервера

| Эндпоинт | Поведение |
|---|---|
| POST `/ru-kz/niv/users/sign_in` | Возвращает куки сессии и CSRF токен |
| GET `/appointment/address/134` | Возвращает адрес Астаны |
| GET `/appointment/days/134.json` | Возвращает массив дат (настраивается) |
| GET `/appointment/times/134.json` | Возвращает `available_times` |
| POST `/appointment` | Имитирует успешный перенос |
| Режим 429 | Имитирует бан для тестирования антибан логики |

### 2.2 Сценарии для тестирования на моке

- Нет доступных дат — бот ничего не делает
- Есть дата но она ближе 2 месяцев — бот пропускает
- Есть подходящая дата — бот переносит автоматически
- `attempts_left == 1` — бот уведомляет агента, не переносит без подтверждения
- `attempts_left == 0` — бот ставит статус `blocked`, уведомляет агента
- Сервер вернул 429 — бот уходит в паузу на 3 часа
- Сессия протухла — бот перелогинивается автоматически
- В аккаунте 2 заявителя — оба переносятся одновременно

## 3. Фаза 2 — Telegram бот (интерфейс агента)

### 3.1 Команды агента

| Команда | Действие |
|---|---|
| `/start` | Главное меню со статусом системы |
| `/add_client` | Пошаговый онбординг нового клиента |
| `/clients` | Список всех клиентов с текущим статусом |
| `/pause [id]` | Поставить клиента на паузу |
| `/resume [id]` | Возобновить мониторинг клиента |
| `/logs [id]` | История действий по клиенту |
| `/status` | Статус самого бота (работает / на паузе) |

### 3.2 Онбординг нового клиента (/add_client)

1. Бот спрашивает: имя клиента
2. Бот спрашивает: email от аккаунта на сайте
3. Бот спрашивает: пароль
4. Бот логинится в аккаунт автоматически
5. Бот парсит `schedule_id` и `applicant_ids` из страницы
6. Бот показывает найденные данные агенту для подтверждения
7. Агент подтверждает — клиент сохраняется в Supabase
8. Мониторинг начинается автоматически

### 3.3 Уведомления агенту

**Успешный перенос:**

**Аккаунт заблокирован:**

## 4. Антибан стратегия

| Мера | Реализация |
|---|---|
| Рандомный интервал | Cron каждые 5-8 минут (Math.random) |
| Задержка между клиентами | 10-15 секунд рандомно |
| Задержка между запросами | 2-5 секунд внутри одной сессии |
| User-Agent | Реальный браузерный User-Agent из HAR |
| Обработка 429 | Авто-пауза на 3 часа + уведомление агента |
| Переиспользование сессии | Сохраняем куки, перелогин только при протухании |
| Один аккаунт — один поток | Никаких параллельных запросов под одним логином |

## 6. Критически важные моменты для разработчика

- **Лимит 3 попытки** — самое важное. Любой баг в логике счётчика = потеря попытки клиента. Тестировать этот блок максимально тщательно через мок.
- **CSRF токен** обязателен для всех POST запросов. Берётся из HTML страницы после логина. Без него — 422 ошибка.
- **Два запроса всегда парой**: сначала `/address/134` потом `/days/134.json`. Нельзя пропускать первый.
- **applicant_ids передаются в URL как массив**: `applicants[]=111&applicants[]=222`. Сайт показывает только даты где есть места для всей группы.
- **Часовой пояс**: сервер Railway работает на UTC. Все даты хранить и сравнивать в UTC+5 (Астана).
- **Пароли клиентов шифровать** в базе. Не хранить в открытом виде никогда.
- **После успешного переноса** — статус клиента ставить `done`, мониторинг останавливать.
- **Facility ID**: Астана = 134, Алматы = 135. В текущей версии используем только 134.
